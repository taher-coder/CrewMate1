Phase 0 — Backend foundations

Done & verified

The database layer that every other phase depends on. Already built, already run against a real Postgres+PostGIS instance, already proven with a scripted end-to-end test.

Delivered

Phase 1 — Auth & app shell

Next

Nobody can use any app until signup/login produces a real profiles row with the right role. This phase is small but blocks everything after it.

Build

  • Next.js monorepo structure (customer / company / worker / admin as route groups or separate apps — decide in this phase)
  • Supabase Auth: phone+OTP and Google login (sec 5.1)
  • on_auth_user_created trigger → auto-creates profiles row, defaults to customer role
  • Role-based routing guard (a customer login never reaches company/worker/admin UI)
  • Company-owner and worker accounts are role-upgraded by invite/approval flow, never self-selected at signup

Connectors / infra needed

SupabaseTwilio (OTP)VercelGitHub

None of these are connected yet — this is the first phase that actually needs them live, not just planned.

Decision needed: one Next.js app with role-based routing, or four separate deployables? Four is cleaner for independent release cadence (company portal ships faster than worker app); one is simpler to maintain early. Recommendation for MVP: one app, role-gated routes — split later if release cadence demands it.
Exit criteria: a new phone number can sign up via OTP and land in the customer app with a real DB-backed profile; an invited worker can activate their account and land in the worker app.

Phase 2 — Matching engine

Pending

This is the one piece of real business logic the schema deliberately left outside the database (by design — see docs/schema.md). Build it before the customer app's booking flow, because booking has nothing to show without it.

Build

  • Server-side function: given a new request, find eligible companies — verified status, service category enabled, coverage area contains the request's location (PostGIS ST_DWithin query against company_service_areas)
  • Insert request_offers rows for each eligible company — this alone flips the request to companies_notified (trigger already handles this)
  • Expiry sweep: offers past expires_at auto-mark expired; if all offers on a request expire/reject, flip to no_match
  • No-match handling: sec 10.4 — never leave a request spinning

Where it runs

  • Supabase Edge Function (recommended) or a Next.js server action, triggered on request insert
  • Scheduled job (cron / Supabase pg_cron) for the expiry sweep
Exit criteria: a seeded request in a covered area produces real request_offers rows for the right companies within seconds; an uncovered area correctly produces no_match.

Phase 3 — Customer app MVP

Pending

The consumer-facing loop: discover a service, submit a request, watch it get matched, track the job, review it. Sections 5.2–5.9.

Screens

  • Home (categories, search, active/recent bookings)
  • 8-stage booking flow (service → problem → description → media upload → address → time → review → confirm)
  • Matching-state screen, driven live off requests.status — never a fake "accepted"
  • Booking detail + status timeline + messaging
  • Bookings list (Upcoming / Active / Completed / Cancelled)
  • Review submission (gated server-side already — sec 5.10)

Depends on

  • Phase 1 (auth) and Phase 2 (matching) — can't test this flow end-to-end without both
  • Supabase Storage for photo/video upload (request_media)
  • Realtime subscription on requests/jobs for live status updates
Exit criteria: a real customer can submit a request, see it move through matching states truthfully, and — once a company/worker exist (Phase 4/5) — track a job to completion and leave a review.

Phase 4 — Company portal MVP

Pending

Without this, there is no supply side to test Phase 3 against. Sections 6–7.

Build

  • Application form (sec 6.1) + document upload (private Storage bucket)
  • Dashboard — real metrics off live tables, not placeholders
  • Requests inbox → accept/reject (writes to request_offers)
  • Dispatch screen → assign_worker RPC
  • Worker management (invite, activate/deactivate, assign services)
  • Services & service-area configuration
  • Jobs list + job detail workspace

Note

Verification itself (admin approving the application) needs some admin surface — build the minimum needed here (a simple approve/reject screen or even a Supabase Studio-driven process) rather than waiting for the full Phase 6 admin platform.

Exit criteria: a company can apply, get manually verified, configure Plumbing/Ahmedabad coverage, receive a real offer from Phase 2's matching engine, accept it, and assign a worker.

Phase 5 — Worker app MVP

Pending

Closes the loop: the worker is who actually makes jobs.status move. Sections 8.1–8.9. Mobile-first — this one gets used standing in someone's kitchen.

Build

  • Invite acceptance flow (links to Phase 1 auth)
  • Home (today's jobs, next job, availability toggle)
  • Job list + job detail (customer info, address/map, problem, media)
  • Lifecycle buttons wired to advance_job_status RPC — UI should only ever show the one legal next action
  • Completion flow (notes + photos → job_completions)
  • Messaging

Depends on

  • Phase 4 (a company and worker must exist)
  • Maps provider for address display — decision needed, see below
Decision needed: the blueprint names Google Maps, but there's no Google Maps MCP connector available — Mapbox or TomTom are connectable now, or Google Maps goes in via API key directly in code (no connector needed either way for a map embed). Recommend: decide this once, before Phase 3 and Phase 5 both need it.
Exit criteria: a worker receives a real assignment, cannot skip a lifecycle step (already DB-enforced, but the UI should make illegal states un-clickable), and completes a job end-to-end.

Phase 8 — Payments & commissions

Pending

Section 12. Deliberately last among the core flows — the blueprint itself says the platform must not pretend to have collected money (sec 9.9), and the schema already refuses any client write to payments/commissions. This phase is building the one legitimate writer.

Build

  • Quote flow (company proposes, customer accepts — quotes/quote_items)
  • Razorpay checkout integration in the customer app
  • Razorpay webhook handler (Supabase Edge Function, service_role) — the only code allowed to write payments
  • Commission calculation off companies.commission_rate at payment-capture time
  • Payout batching (company earnings view already has the read side built)

Connectors needed

Razorpay
Exit criteria: a test payment captures via webhook, a commission row is created automatically, and the company's earnings dashboard reflects it — with zero client-side code able to fake any of it.
